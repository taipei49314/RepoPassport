# Manifest Contract

`repo-passport.yml` is the human-authored contract. Its decoded JSON form MUST validate against `schemas/repo-passport.schema.json`, then pass the semantic checks in `core.md`.

## Root

```yaml
apiVersion: repopass.dev/v1alpha1
kind: RepositoryPassport
metadata:
  name: example-project
spec:
  project: {}
  environments: {}
  scenarios: {}
  policies: {}
  evidence: {}
```

All root members are required. Unknown members fail validation unless their name begins with `x-` and matches the extension-name pattern.

## Metadata

| Field | Meaning |
|---|---|
| `metadata.name` | Stable manifest identifier. |
| `metadata.displayName` | Optional human-readable name. |
| `metadata.description` | Optional human-readable description. |
| `metadata.maintainers[].name` | Declarative maintainer label. It is not verified identity. |
| `metadata.maintainers[].url` | Optional URI associated with the declaration. |
| `metadata.labels` | Free-form string labels with lowercase keys. |

## Project

| Field | Meaning |
|---|---|
| `spec.project.kind` | One of `cli`, `web-app`, `api`, `library`, `notebook`, `model`, `dataset`, `documentation`, `desktop-app`, `mobile-app`, or `unknown`. |
| `spec.project.audiences[]` | Intended audiences. Values are `end-user`, `student`, `developer`, `maintainer`, `security`, or `automation`. |
| `spec.project.entrypoints[]` | Scenario names presented as supported entrypoints. |

Every entrypoint MUST resolve to a key in `spec.scenarios`.

## Environments

Each `spec.environments.<name>` contains:

| Field | Meaning |
|---|---|
| `platform.os` | `linux` in v1alpha1. |
| `platform.architecture` | `amd64` or `arm64`. Availability remains runner-dependent. |
| `runtime.adapter` | `node` or `python`. |
| `runtime.version` | Authoring constraint. The resolver MUST replace it with one exact semantic version. |
| `baseImage.reference` | Authoring image reference. The resolver MUST replace any tag with an immutable SHA-256 digest. |
| `resources.cpu` | Positive CPU limit expressed as cores. |
| `resources.memory` | IEC memory size. |
| `resources.disk` | IEC writable-disk limit. |
| `resources.pids` | Positive process count limit. |
| `resources.time` | Optional overall duration limit. |
| `resources.logBytes` | Optional combined bounded-log limit. |
| `requiredServices[]` | Optional service identifiers needed by the environment. |
| `requiredRunnerFeatures[]` | Features that must be negotiated before execution. |

`latest` and other mutable image tags MAY appear while authoring, but a verified plan MUST contain only `baseImageDigest`. A resolver that cannot obtain a digest fails with `MUTABLE_BASE_IMAGE` or `PLAN_UNRESOLVED`.

## Scenarios

Each `spec.scenarios.<name>` contains:

| Field | Meaning |
|---|---|
| `title`, `description`, `purpose` | Human-facing documentation. |
| `audience` | Primary audience for this scenario. |
| `environment` | Name of one environment. |
| `inputs` | Typed fixture or user-input declarations. |
| `phases` | Ordered execution declarations described in `scenario-model.md`. |
| `capabilities` | Phase-specific declarations described in `capability-model.md`. |
| `secrets` | Scenario-scoped synthetic secret declarations. |
| `verification` | Repetition, observer, stability, and cleanup requirements. |

Secrets are intentionally scenario-scoped. There is no `spec.secrets` field in v1alpha1.

### Inputs

Input types are:

```text
string
integer
boolean
file
directory
json
secret-reference
choice
```

All inputs declare `type` and `required`. File and directory inputs also declare an absolute sandbox `mount.path` and `mount.readOnly: true`. A `choice` input declares nonempty `choices`. A `secret-reference` cannot carry a fixture, mount, or literal value.

Repository fixtures use relative POSIX paths and MUST remain inside the immutable source snapshot. Public verification SHOULD use repository fixtures or deterministic synthetic input.

### Secrets

The only v1alpha1 secret shape is:

```yaml
secrets:
  api-key:
    source: synthetic
    scope:
      phases: [exercise]
    exposeAs:
      env: API_KEY
```

The manifest has no secret-value field. `value`, `literal`, inline token, user credential, vault credential, and host environment inheritance are not secret sources in v1alpha1. Such declarations MUST fail validation. Synthetic values are generated by the trusted runner, scoped to the listed phases, redacted from logs, and never serialized into a resolved plan or report.

The literal-secret rule applies to declared credentials; validators MUST also reject obvious raw credential fields such as `password`, `token`, `apiKey`, `authorization`, or `clientSecret` when they occur outside an `x-` extension. It does not claim that arbitrary strings can be perfectly classified as secret.

### Verification

| Field | Meaning |
|---|---|
| `repeats` | Requested fresh-sandbox runs, from 1 through 100. |
| `successThreshold` | Minimum matching successful runs. It MUST be no greater than `repeats`. |
| `requiredObservers[]` | Observer names that must be available. |
| `cleanup.allowedResidue[]` | The only sandbox paths allowed after cleanup. |
| `stabilityRule` | `all-matching` or `threshold-matching`; default is `all-matching`. |
| `resourceVariancePercent` | Optional allowed percentage variance for resource stability. |

Required observer names are `process-exec`, `filesystem-write`, `port-listen`, `network-enforcement`, and `resource-usage`.

## Policies

`spec.policies.profile` selects a versioned policy profile such as `baseline-v1`. The resolver MUST bind the profile to an immutable `policyBundleDigest`. A floating or unavailable profile fails with `POLICY_BUNDLE_UNRESOLVED`.

## Evidence

`spec.evidence.profile` is `minimal-public` or `local-full`.

Supported include values:

```text
verification-summary
normalized-observations
sbom
```

Supported exclude values:

```text
raw-stdout
raw-stderr
raw-syscall-trace
```

An evidence profile controls packaging, not the verifier's internal inputs. Excluding a raw trace does not remove its digest or any normalized facts needed by a verdict.

## Extensions and unknown fields

Objects explicitly marked extensible by the schema MAY contain `x-<name>` members. The core validator preserves extension content in the manifest digest but assigns it no core semantics.

Every other unknown field is a validation error with `MANIFEST_UNKNOWN_FIELD`. Misspellings are never ignored. A runner or plugin MUST NOT silently interpret an extension as weakening a core policy, capability, observer requirement, or verdict rule.
